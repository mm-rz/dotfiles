# dotfiles インストーラーを保守する

初期環境での実行要件を増やさず、`install.sh` をリポジトリ内のファイルやツールと一致させる。

## 編集前に調査する

1. `install.sh`、`README.md`、変更対象ツールの設定を読む。
2. `git status --short` を実行し、ユーザーによる無関係な変更を保持する。
3. 次の項目を分けて確認する。
   - 実行時に必要なパッケージとコマンド
   - ビルド時の依存関係
   - リンクが必要な設定ファイルのパス
   - ツールを導入すべきプロファイル
4. `.zshrc`、`zsh/`、`.config/`、`tmux/` から実行される外部コマンドを検索し、導入漏れを確認する。コメント内の例と実際に有効な設定を区別する。
5. 依存関係に関するチャートを `README.md` になければ追記する。あれば実装と照合し、依存関係やプロファイルが変わった場合に更新する。

## 現行のプロファイル設計を保つ

プロファイルを `minimal` → `server` → `developer` → `desktop` の累積的な段階として扱う。上位プロファイルには下位プロファイルの機能を含める。

- `minimal`: zshと、その設定を読み込んだ直後から参照されるCLIツールを導入する。シェル設定をリンクする時点で、Sheldon、Starship、zoxide、lsd、fzf、direnvなどが利用可能であることを保証する。
- `server`: `minimal` にNeovimとその設定を追加する。これをデフォルトプロファイルとする。
- `developer`: `server` にPython系開発ツール、検索ツール、Go、Voltaを追加する。
- `desktop`: `developer` にNiri、WezTerm、CaskaydiaMono Nerd Font、およびNiri設定から実行されるWayland周辺ツールを追加する。

ツールは、それを参照する設定がリンクされる段階より後へ配置しない。たとえばYaziを `minimal` で導入するなら、Yaziの設定とプレビューに使う `bat` も同段階で利用可能にする。デスクトップ設定に実行コマンドを追加した場合は、`desktop` でそのコマンドを導入するか、意図的な外部依存であることをユーザーに確認する。

この割り当てを変更する明示的な依頼があれば、`install.sh`、READMEの図表、この節を同時に更新する。個々のツールの最新一覧は重複記載せず、常に `install.sh` を正とする。

## 不変条件を守る

- インストーラーは POSIX `sh` で記述する。Bash の配列、`[[ ... ]]`、`source`、プロセス置換、`pipefail` を導入しない。
- 外部ツールの公式インストーラーが POSIX `sh` 以外のシェルを指定している場合は例外とする。公式ドキュメントで指定シェルを確認し、そのシェルを先にパッケージとして導入したうえで、ダウンロードした一時ファイルを指定シェルで明示的に実行する。`install.sh` 本体や自作の補助処理を非 POSIX にする根拠にはしない。
- 言語ランタイム、ダウンロードツール、パッケージマネージャーのラッパー、dotfiles マネージャーが導入済みであると仮定しない。OS の標準機能と `git` だけが存在するものとする。
- コンポーネントを小さく保ち、各 `install_<component>` 関数に明確な責務を1つだけ持たせる。
- 前提コンポーネントを `component_dependencies` に宣言する。プロファイル内の記述順だけに依存しない。
- プロファイルを環境の役割ごとに保つ。デスクトップで利用できるという理由だけで、GUI ツールを `minimal`、`server`、`developer` に追加しない。
- 再実行を安全にする。可能な限り、再インストールや置換の前にコマンドの存在とリンク先が正しいか確認する。
- 既存のリンク先を上書きせず、バックアップする。
- 実行可能なインストーラーは一時ファイルへダウンロードしてから実行する。`curl | sh` のパイプラインを追加しない。
- 対応するパッケージマネージャーを明示する。現在は `apt-get` のみを対象とし、未検証のクロスプラットフォーム対応をうたわない。
- `--dry-run` では環境を変更しない。インストーラーの保守中に実際のインストールを実行しない。
- リポジトリのclone先を `$HOME/dotfiles` に固定しない。リンクされた `.zshrc` などからリポジトリ位置を解決し、同じ設定や初期化処理を重複して読み込まない。
- 設定が指定するフォント名、実行ファイル名、Ubuntu上の別名をインストール結果と一致させる。現在の標準フォントはWezTerm設定に合わせたCaskaydiaMono Nerd Fontとする。

## ツールを更新する

ツールを追加または変更するときは、該当するすべての接続点を更新する。

1. `component_dependencies` のコンポーネントと依存関係を追加または調整する。
2. 対応する `install_<component>` 関数を追加または調整する。
3. 適切なプロファイルだけにコンポーネントを追加する。
4. 設定ファイルを、対象範囲が最も狭い `links-*` コンポーネント（core、editor、desktop）でリンクする。
5. 公開インターフェースやプロファイルの内容を変えた場合は、`list_items`、ヘルプ、`README.md` を更新する。

導入手順と対象プロファイルが一致する場合は、既存のコンポーネントを優先する。依存関係が独立している、異なる環境で任意選択になる、または `--only` や `--skip` で個別に選択する必要がある場合は、新しいコンポーネントを作る。

対応済みパッケージマネージャーから導入できないツールについて、パッケージ名を推測したり、別のインストーラーを暗黙に追加したりしない。導入元の選択がセキュリティ、更新方法、対応環境に大きく影響する場合は、意図を確認するかユーザーに質問する。

Ubuntuの対象バージョンと `apt-cache` を確認し、パッケージがなければ公式ドキュメントまたは公式リポジトリから現在の導入方法を検証する。現行方針ではNiriとawwwを公式ソースからビルドし、WezTermを公式APTリポジトリから導入する。上流の提供方法が変わった可能性がある場合は再検証する。実行スクリプトは一時ファイルへ保存し、公式に対応していればシェル設定を変更しないオプションを使う。

明白な不整合はインストーラーと同時に直す。例として、存在しないコマンド名、通常版パッケージにないオプション、自作の POSIX `sh` 補助スクリプトのBashism、公式インストーラーが指定するシェルとの不一致、同じ初期化処理の二重実行が該当する。導入元、対応環境、ユーザーの好みに関わる選択は推測せず質問する。

## READMEの依存図を更新する

READMEのMermaid図では、抽象的なコンポーネント名だけのノードを作らない。次を満たす。

1. `minimal`、`server`、`developer`、`desktop` で初めて追加される内容を別々のsubgraphにする。
2. 上位プロファイルが下位プロファイルを包含することを本文で明記する。
3. 各ノードにコンポーネント名と、導入される主要なツール名またはパッケージ名を併記する。
4. 実線の矢印をインストール依存関係として、前提から利用側へ向ける。
5. 図の後に、直前のプロファイルから追加されるツールを比較する表を置く。

図と表は `profile_components`、`component_dependencies`、各 `install_<component>` 関数から再構成し、READMEだけに存在するツールや省略された主要ツールを残さない。

## 検証する

インストーラーを変更したら、リポジトリのルートで次を実行する。

```sh
sh -n install.sh
./install.sh --list
./install.sh --dry-run --profile minimal
./install.sh --dry-run --profile server
./install.sh --dry-run --profile developer
./install.sh --dry-run --profile desktop
git diff --check
```

新規または変更したコンポーネントごとに、`--only` を指定した dry-run も実行する。依存コンポーネントを `--skip` する矛盾した指定を1つテストし、分かりやすいエラーで失敗することを確認する。ShellCheck が利用可能なら `shellcheck -s sh install.sh` も実行する。

出力された `Plan:` を確認し、依存先が利用側より前にあり、対象外の環境に影響していないことを確かめる。最後に差分全体を確認する。ユーザーから明示的な依頼がない限り、dry-run ではないインストールを実行しない。
